# Recipe under Constraints — правила роботи для Claude Code

Технолог описує словами бажаний продукт («полуничний йогурт без молока, білка не менше, ніж у звичайного,
до 45 грн/кг, claim "зі зниженим вмістом цукру"»). Сервіс повертає рецептуру в г/кг або пояснює,
чому її не існує і яке мінімальне послаблення обмежень робить задачу розв'язною.

## Стек

Python 3.12 (uv), FastAPI, PostgreSQL 16 через asyncpg (SQL-міграції `migrations/*.sql`, ідемпотентні,
застосовуються на старті), pydantic v2, PuLP + HiGHS (LP-солвер; не CBC з `pulp[cbc]` — хибна недосяжність), pytest, ruff.
Docker / docker compose. LLM: Gemini (за замовчуванням) або Groq — лише безкоштовні тарифи без картки.

## Архітектура (зафіксована)

```
текст → [1. Парсинг: LLM → Constraints (Pydantic)]          app/parsing.py
      → [2. Бізнес-правила claims → лінійні обмеження]      app/claims.py
      → [3. Солвер LP (diet problem) над каталогом]         app/solver.py
      → [4. Недосяжність → мінімальне послаблення]          app/relax.py
      → [5. Пояснення: LLM над уже порахованими фактами]    app/explain.py
      → відповідь: рецептура г/кг + перевірка кожного обмеження (факт vs ліміт)
```

## Правила

- **Нутрієнти, вартість і перевірку обмежень рахує тільки детермінований Python (солвер). LLM ніколи
  не рахує числа** — лише (1) парсить текст у структуровані обмеження і (2) переказує готові факти.
  Числа в поясненні беруться з результату солвера, а не з відповіді моделі.
- LLM викликається тільки через `LLMClient` (`app/llm/`); провайдер обирає `LLM_PROVIDER` (gemini | groq | fake).
- Тести не ходять у мережу: тільки `FakeLLM`.
- Ніколи не питати користувача про уточнення в рантаймі. Невизначеність → явне припущення
  в розділі «Припущення» нижче і в README.
- Невідомий/кривий запит → структурована помилка 4xx або пояснення, ніколи не 500.
- Claims — бізнес-правила з посиланням на норму (напр. reduced sugar, Reg. (EC) 1924/2006, Annex:
  цукор ≥30 % нижче за порівнюваний продукт І енергія не вища).
- Ціни інгредієнтів вигадані, але правдоподібні; порядок цифр пояснено в каталозі, позначено як оцінку.
- Секрети тільки в `.env` (не комітиться); нові змінні — в `.env.example`.
- Один коміт на задачу (`KAN-NN: ...`); задача закрита лише після ручної перевірки критеріїв.

## Структура

Повна схема — у `README.md` («Структура»). Ключове: `app/pipeline.py` (`run_recipe`) — спільний
пайплайн API і `eval/proof.py`, не дублювати його логіку; дані — `data/*.yaml`; доказ — `eval/`.

## Команди

- `make up` / `make down` — сервіс і БД (docker compose), `localhost:${API_PORT:-8000}`: `POST /recipe`, `/docs`, `/health`
- `make test` — pytest без мережі й ключів (FakeLLM); `make lint` — ruff
- `make proof` — `eval/requests.jsonl` через `POST /recipe` з живою LLM, незалежна перевірка з
  `data/*.yaml` → таблиця + `eval/proof_report.md`, код виходу 1 при fail; `ARGS="--url http://api:8000"`
  — проти запущеного сервісу. Не підганяти каталог/промпт під `requests.jsonl`.

## Припущення

Повний список — у `README.md`, розділ «Припущення»; кожне звірене з кодом. Нове припущення (рішення
замість уточнювального питання) дописувати туди, з посиланням на файл, де воно закладене.
