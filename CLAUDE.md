# Recipe under Constraints — правила роботи для Claude Code

Технолог описує словами бажаний продукт («полуничний йогурт без молока, білка не менше, ніж у звичайного,
до 45 грн/кг, claim "зі зниженим вмістом цукру"»). Сервіс повертає рецептуру в г/кг або пояснює,
чому її не існує і яке мінімальне послаблення обмежень робить задачу розв'язною.

## Стек

Python 3.12 (uv), FastAPI, PostgreSQL 16 через asyncpg (SQL-міграції `migrations/*.sql`, ідемпотентні,
застосовуються на старті), pydantic v2, PuLP + CBC (LP-солвер), pytest, ruff.
Docker / docker compose. LLM: Gemini (за замовчуванням) або Groq — лише безкоштовні тарифи без картки.

## Архітектура (зафіксована)

```
текст → [1. Парсинг: LLM → Constraints (Pydantic)]          app/parsing/
      → [2. Бізнес-правила claims → лінійні обмеження]      app/claims/
      → [3. Солвер LP (diet problem) над каталогом]         app/solver/
      → [4. Недосяжність → мінімальне послаблення]          app/solver/
      → [5. Пояснення: LLM над уже порахованими фактами]    app/explain/
      → відповідь: рецептура г/кг + перевірка кожного обмеження (факт vs ліміт)
```

## Правила

- **Нутрієнти, вартість і перевірку обмежень рахує тільки детермінований Python (солвер). LLM ніколи
  не рахує числа** — лише (1) парсить текст у структуровані обмеження і (2) переказує готові факти.
  Числа в поясненні беруться з результату солвера, а не з відповіді моделі.
- LLM викликається тільки через `LLMClient` (`app/llm/`); провайдер обирає `LLM_PROVIDER` (gemini | groq | fake).
- Тести не ходять у мережу: тільки `FakeLLM`.
- Ніколи не питати користувача про уточнення в рантаймі. Невизначеність → явне припущення
  в розділі «Припущення» нижче і в README.
- Невідомий/кривий запит → структурована помилка 4xx або пояснення, ніколи не 500.
- Claims — бізнес-правила з посиланням на норму (напр. reduced sugar, Reg. (EC) 1924/2006, Annex:
  цукор ≥30 % нижче за порівнюваний продукт І енергія не вища).
- Ціни інгредієнтів вигадані, але правдоподібні; порядок цифр пояснено в каталозі, позначено як оцінку.
- Секрети тільки в `.env` (не комітиться); нові змінні — в `.env.example`.
- Один коміт на задачу (`KAN-NN: ...`); задача закрита лише після ручної перевірки критеріїв.

## Структура

```
app/
  llm/        # LLMClient + провайдери (gemini, groq, fake)
  parsing/    # вільний текст → Constraints
  claims/     # правила claims → обмеження
  solver/     # LP, перевірка, діагностика недосяжності
  explain/    # людське пояснення над фактами солвера
data/         # каталог інгредієнтів і шаблони рецептур (YAML)
migrations/   # SQL-міграції (ідемпотентні, на кожному старті)
scripts/      # харнес доказу: незалежна перевірка рецептури
tests/
```

## Припущення

<!-- Кожна задача дописує сюди по одному пункту; README дублює цей список. -->
- (KAN-42) Каталог: 3 шаблони (фруктовий йогурт, гранола-бар, пшеничний хліб), дані в `data/*.yaml`.
  «Звичайний» продукт = `base_recipe` шаблону. Рецептура — г на 1 кг суміші до термообробки (усушку
  при випіканні не моделюємо). Нутрієнти за правилами ЄС 1169/2011 (вуглеводи без клітковини, поліоли
  не цукри, еритрит 0 ккал; алюлоза — моносахарид, тож рахується як цукор). Ціни вигадані, порядок
  величин пояснено в `price_source` кожного інгредієнта.
- (KAN-43) Парсинг: LLM лише виписує факти з тексту, нічого не рахує й не перераховує одиниці.
  «Білка не менше N г» — г на 100 г продукту. Ціна — лише в грн/кг; інша одиниця (за 100 г, за
  упаковку) не конвертується, а йде в `notes`. «Без молока» / веганський → виключити `milk`;
  «безлактозний» — не виключає молоко. Невідомий продукт → `matched_template: null` з причиною.
- (KAN-44) «Зі зниженим вмістом цукру»: цукор ≤ 70 % і ккал ≤ «звичайного» продукту (`base_recipe`),
  обидва на 100 г (Reg. 1924/2006 Annex + 1047/2012; наказ МОЗ № 1145, дод. 1, п. 23). Рівно 30 %
  проходить. Якщо у звичайному продукті цукру немає — claim неможливий.
